# `.MDZ` — MLD (Sharp X68000, FM + PCM + MIDI 동시 구동)

> **작성**: JJOME (GitHub [jihodaya](https://github.com/jihodaya)) — [JMPlayer](https://github.com/jihodaya/jmplayer) 포맷 분석 기록
> **최초 정리**: 2026-09-28 · **라이선스**: [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/deed.ko) — 인용 시 작성자와 출처를 밝혀 주세요.
> **근거**: MLD 패키지(`MLD247.LZH`, NFG Games의 x68pub 미러 `SOUND/MLD/`)의 **MML 컴파일러 `mlc.x`**와 역변환기 **`mdz2mus.x`**를 run68x로 Windows에서 실행. MML을 컴파일해서 나온 바이트를 읽고, 176곡을 역변환→재컴파일해 트랙별 틱 수를 대조.
> 표시: ✅ 확인됨 · 📏 실측으로 맞춤 · ❓ 미확인 ([README](README.md) 참고) · [English](en/mdz-mld.md)

**MLD**는 LUM2가 만든(1990~93) X68000 음악 드라이버다. OPM(FM), ADPCM, **외부 MIDI
모듈**을 **한 곡 안에서 동시에** 움직인다. 매뉴얼은 스스로를 "MXDRV + MDD 같은"
드라이버라고 소개하는데, 그게 함정이다. **머리, 오프셋 표, `F1 00` 끝 표시는 MDX와
같지만 명령은 다르다.** 그리고 확장자가 아무것도 말해 주지 않는다 — 같은 모음집 안에
FM만 쓰는 `.mdz`도, 실제로는 MLD인 `.mdx`도 있어서 **내용을 보고** 판별해야 한다.

모든 수는 **빅 엔디언**이다.

## 1. 기준 답안 — 컴파일러 자체

MLD 패키지에는 이 파일을 만든 **컴파일러 `mlc.x`**와 역변환기 `mdz2mus.x`, 57 KB
매뉴얼 `mlc.doc`이 들어 있다. 둘 다 Human68k 콘솔 프로그램이고,
**`run68x`**(github `kg68k/run68x`, win-x64 빌드)로 롬도 OS도 없이 Windows에서
돌아간다. 그래서 이 포맷에 대한 질문은 **MML을 써서 컴파일하고 바이트를 읽으면**
답이 나온다.

```
A C1     V105   @v115  p64    @16    @t228  y91,40    o4 c4  r4
  E1 10  E3 16  FB 8C  FC 40  FD 10  FF E4  FE 5B 28  3C 30  80 30
```

⚠️ **짧은 폴더에서 실행할 것.** Human68k는 경로 길이 제한이 있어서 긴 경로에서는
`ファイルのパス名が長すぎます`로 모두 실패한다. 에뮬레이터가 고장 난 것처럼 보인다.

`mlc.x -n 파일.mus`는 **트랙마다 클럭(틱) 수**를 알려 준다. 이것이 타이밍의 정답이다.
176곡을 역변환하고 다시 컴파일해서 우리 해석의 트랙별 틱 수와 비교했다. 처음
**65.9%**였던 일치가 **94.5%**가 됐다.

## 2. 머리 — 오프셋 표의 폭이 두 가지

```
제목  0D 0A 1A  PDX 이름  00  [오프셋 표]
오프셋 표 = 음색표 오프셋, 트랙 오프셋 × N   (표의 시작 기준)
```

✅ **표의 항목이 곡마다 2바이트이거나 4바이트다.** 파일에 어느 쪽인지 적혀 있지
않다. 4바이트 형식은 같은 표에 모든 항목의 상위 워드가 0인 것이다. 2바이트로 먼저
시도하고 안 맞으면 4바이트로 시도한다.

> 4바이트 형식을 몰랐을 때 해당 곡은 **오류 없이 로드되고 무음으로 재생**됐다.
> 옛 모음집 176곡 중 18곡(같은 파일 10개인 `Bahnwelt*gs` 포함)과 GRADIUS II 7곡이
> 그랬다. 실패가 "무음"으로 나타나는 포맷은 "로드되는가"가 아니라 "뭔가 나오는가"를
> 검사해야 한다.

표의 시작 위치를 찾는 방법은 MDX와 같다([mdx.md](mdx.md) 1절).

## 3. 트랙이 무엇을 움직이는가 — `0xE1`

✅ 트랙은 `0xE1`로 대상을 정한다. **피연산자의 비트 4 하나가 전부다.**

| MML | 바이트 | 대상 |
|---|---|---|
| `C1`~`C16` | `E1 10`~`E1 1F` | MIDI 채널 1~16 (`0x10 \| (ch−1)`) |
| `CH1`~ | `E1 00`~ | OPM(FM) 채널 |
| `CHP1` | | ADPCM |

✅ 트랙 첫 부분만 보고 판별하되, **익스클루시브(아래)는 통째로 건너뛰고** 64바이트를
센다. 어떤 트랙은 첫 64바이트가 1.5 KB 익스클루시브 안에 들어 있다. 그렇다고
0x80 미만 바이트에서 멈추면 피연산자를 음표로 오인해서 FM 곡 27개 중 19개를 놓친다.

✅ 트랙은 곡 중간에 `0xE1`로 대상을 바꿀 수 있다.

모음집 158곡(MIDI 있음) 중 **146곡은 MIDI만**, **12곡은 FM/PCM과 MIDI를 함께**
쓴다. 곡 제목이 대놓고 말해 준다: `For SC55+X680x0`, `for CM-64+PCM8`,
`SC-55+OPM+ADPCM`.

## 4. 음표와 시간

- ✅ 음표는 **MIDI 음 번호 그대로**(`c4` → `3C` = 60) + 길이 바이트. `0x80`은 쉼표.
- ✅ **4분음표 = 48틱** (`r4` → `80 30`).
- ✅ **FM 트랙도 같은 명령 바이트를 쓴다.** `CH1 c4`는 `E1 00 3C 30`이다. 그래서
  FM 쪽에 필요한 것은 새 시퀀서가 아니라 **출력부**다.
- ✅ **FM 음정 = MXDRV 음 번호 (MIDI 음 − 15), 키 분수 `0x14`.** X68000은 OPM을
  4 MHz로 돌리는데 칩의 키 코드는 3.58 MHz 기준이라 1.92반음 차이가 난다. MXDRV는
  음 번호와 키 분수 5/64로 이것을 흡수한다(MDX 음 45가 261.1 Hz = MIDI 60).
  MLD는 FM 트랙에도 `c4`를 60으로 적으므로 −15를 해야 **MIDI 파트와 같은 음정**이
  된다. 곡 자체가 증거다: `ken_pcm`의 FM 트랙은 MIDI 트랙과 음표가 하나하나 같다.
  같은 음을 겹치도록 만든 드라이버라면 `c4`가 양쪽에서 같은 음이어야 한다.
- ✅ **드라이버의 초기 템포는 타이머 B `0xC8`**(`mld.x` 상주 코드 세 곳의
  `move.b #$C8,$BA(a5)`)이고, 이것은 약 87.2 BPM이다. 곡의 첫 `@t` 전 구간이 이
  템포로 흐른다. 표준 MIDI의 기본값(120 BPM)을 쓰면 첫 `@t`가 늦게 나오는 곡에서
  MIDI 파트가 FM 파트보다 앞서 간다(GRADIUS II 세트 0.174초).

## 5. MIDI 쪽 명령

| 명령 | MML | 뜻 | |
|---|---|---|---|
| `0xE1` | `C` / `CH` / `CHP` | 대상 (3절) | ✅ |
| `0xE3` | `V` | 메인 볼륨 → CC7. **감쇠값이다: CC7 = 127 − n** | ✅ |
| `0xFB` | `v` / `@v` | 벨로시티. 비트 7 켜짐: `255 − n`. 꺼짐: 16단 곡선 (부록 B) | ✅ |
| `0xFC` | `p` | 팬 → CC10 (그대로) | ✅ |
| `0xFD` | `@` | 프로그램 (그대로) | ✅ |
| `0xE2` | `P` | 서스테인 → CC64 (그대로) | ✅ |
| `0xFE` | `y` | 컨트롤 체인지, 2바이트 | ✅ |
| `0xD6` | | **NRPN 묶음**, 3바이트 → CC99 / CC98 / CC6 | ✅ |
| `0xFF` | `t` / `@t` | 템포 = OPM 타이머 B (클수록 빠름) | ✅ |
| `0xF8` | `q` / `@q` | 게이트. `q1`~`q8`은 음 길이의 8분의 몇, `@qN`은 `255 − N` 클럭으로 저장 | ✅ |
| `0xF6` `0xF5` `0xF4` | `[` `]` `/` | 반복 시작·끝·탈출. **부호 있는 상대 점프** | ✅ |
| `0xF7` | `&` | 붙임줄. **뒤에 오는 음표**에 표시 | ✅ |
| `0xD7` `0xCA` | `EX` / `WEX` | 익스클루시브. `0xF7`까지 | ✅ |
| `0xBD` `0xBE` `0xBF` | 모듈 매크로 | Roland SysEx로 재구성 (아래) | ✅ |
| `0xD0` | `DV` | 장치 번호 (기본 17 = `0x10`) | ✅ |
| `0xF1` | `L` / 끝 | `00`이면 끝, 아니면 무한 루프 점프 | ✅ |

✅ **모듈 매크로는 체크섬까지 정확히 재구성된다.** `#SC:EM1`은
`BE 40 01 30 01 0E F7`로 컴파일된다. `0x40+0x01+0x30+0x01 = 0x72`,
`128 − 0x72 = 0x0E`이므로 저장된 것은 **주소부터 체크섬까지의 Roland 메시지**이고,
드라이버는 `F0 41 <장치> <모델> 12` 머리만 붙인다.

| 명령 | 모델 | 대상 |
|---|---|---|
| `0xBD` | `0x45` | SC-55 디스플레이 |
| `0xBE` | `0x42` | GS |
| `0xBF` | `0x16` | MT-32 / CM-64 |
| `0xB7` `0xBB` | ❓ | 모델 바이트를 몰라서 보내지 않음 (틀린 모델은 안 보내는 것보다 나쁨) |

✅ **익스클루시브와 모듈 매크로는 트랙 대상과 상관없이 MIDI로 나간다.** FM이나
PCM 파트에는 보낼 곳이 없기 때문이다. `NEW_Wa`의 첫 트랙은 PCM 파트(`CHP1`)인데
MT-32 리셋, 파셜 리저브, **CM-32L 음색 다섯 개 업로드**를 담고 있다. MIDI 트랙에서만
익스클루시브를 보내면 이 곡의 MIDI 파트(메모리 음색을 쓰는 9개 파트)가 전부 무음이
된다.

> 처음에는 "음색 데이터가 모음집에 빠져 있다"고 잘못 결론 냈었다. 우리 **변환 결과**에서
> 음색 업로드를 찾았는데, 변환기가 버린 것이니 당연히 없었다. **원본 파일을
> 역변환(`mdz2mus`)해서 확인한 뒤에 결론 낼 것.**

## 6. FM / PCM 쪽

- ✅ `@5`, `@v100`, `V100`, `p2`, `@q7`이 MIDI 쪽과 같은 명령·같은 감쇠 계산으로
  컴파일된다. 다른 점: `p`는 OPM `0xC0`의 스테레오 비트(0~3), `y`는 컨트롤 체인지가
  아니라 **레지스터 직접 쓰기**.
- ✅ `0xEA` = **`MH`, 하드웨어 LFO, 피연산자 5개.** MXDRV의 긴 `0xEA`와 바이트 단위로
  같다(`MH2,207,4,0,0,0,0` → `EA 02 CF 84 00 00`). `E8 10` / `E8 00`은 `MHON` / `MHOF`.
- ✅ `0xEC` = LFO 설정, 피연산자 **5개** (3이 아님).
- ✅ `0xED` = MDX의 `F`(ADPCM 샘플레이트), 피연산자 1개. PCM 트랙 첫머리에 `ED 04`로
  나온다.
- ✅ PCM 출력은 MDX와 같은 X68000 필터를 거친다([mdx.md](mdx.md) 8절).

> `0xEC`를 3개로, `0xED`를 0개로 읽었을 때 `ken_pcm`에서 FM 트랙이 0.88초, 드럼
> 트랙이 1.56초 늦게 시작했다. 틱 합계로 맞추는 방법으로는 이런 오류가 안 잡힌다 —
> 한 줄로 읽어 나가다 다음 명령에서 저절로 다시 맞기 때문이다. **명령 바로 뒤에 오는
> 바이트가 말이 되는지**를 봐야 한다. `0xEC`를 5개로 읽으면 뒤따르는 바이트가 항상
> `E9`/`E8`/`80`이고, 3개로 읽으면 0x00~0x05(들리지 않는 음)였다.

## 7. FM과 MIDI를 맞추는 법 (검증 방법)

두 파트가 같은 박에 있는지는 **FM 키온 시각과 MIDI 음 켜기 시각을 10초 구간마다 맞춰
보는** 방법으로 확인했다. 맞게 겹쳐진 곡은 모든 구간에서 오프셋 0 ms가 나오고,
어긋나면 구간마다 조금씩 밀린다.

✅ 두 모음집(183곡)의 혼합곡 20곡 모두 **모든 구간 0 ms, 밀림 없음.** 컴파일러로 왕복 가능한 16곡은
**모든 트랙의 틱 수가 컴파일러와 일치**한다. (`NEW_Wa`, `Prel_le`, `defeat`는
`mdz2mus`가 만든 MML을 `mlc`가 거부해서 이 방법으로 확인할 수 없다.)

## 8. 미확인

- ❓ 아직 모르는 명령 13종 (피연산자 0개로 넘김). 트랙의 5.5%가 컴파일러 틱 수와
  다르다. 명령 하나의 길이를 바꿔서 더 좋아지는 경우는 없어서, 남은 원인은 구조적인
  것으로 보인다.
- ❓ `0xCD`, `0xD8`: 어떤 MML로도 만들어 내지 못해 틱 수로 길이를 맞췄다.
- ❓ PCM 트랙의 음 번호 → PDX 샘플 대응. `ken_pcm`의 PCM 트랙은 음 36, 38
  (**General MIDI의 킥과 스네어**)을 친다. 인덱스라기보다 표를 거치는 것으로 보인다.
- ❓ 곡이 요구하는 `ADT00SC.PDX`, `gr3_p.pdx`, `dsp.pdz`, `ken.pdz`는 구하지 못했다.
- ⚠️ `ANGE10.mdz`는 반복이 자기 자신으로 닫힌다. 틀린 길이로 읽으면 16,001번
  돈다. 모르는 명령 통계는 **파일별로** 볼 것 — 합계로 보면 이 한 곡이 전체를
  뒤덮는다.

## 부록 B. `v0`~`v15` → 벨로시티

```
0, 7, 15, 23, 31, 39, 47, 55, 64, 71, 79, 87, 95, 103, 111, 119
```
