# `.RCP` — Recomposer (PC-98 / X68000) + `.GSD` 셋업 파일

> **작성**: JJOME (GitHub [jihodaya](https://github.com/jihodaya)) — [JMPlayer](https://github.com/jihodaya/jmplayer) 포맷 분석 기록
> **최초 정리**: 2026-09-28 · **라이선스**: [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/deed.ko) — 인용 시 작성자와 출처를 밝혀 주세요.
> **근거**: 참조 `.MID`가 딸린 Recomposer 곡 **303개**(테스터 제공) + 3개와 대조, 라이브러리 213곡 일괄 변환.
> 표시: ✅ 확인됨 · 📏 실측으로 맞춤 · ❓ 미확인 ([README](README.md) 참고) · [English](en/rcp.md)

일본 COME ON MUSIC의 시퀀서 **Recomposer**(레코포자) 곡 파일이다. RCP 포맷에 대한
공개 자료는 이미 있지만, 참조 MIDI 303곡과 대조해 보면 그대로는 맞지 않는 곳이
많았다. 이 문서는 **대조해서 확인한 해석**을 적는다.

결과: 303곡 중 **225곡이 모든 채널에서 음표까지 일치**, 66곡은 우리 결과가 참조의
앞부분과 정확히 같고 참조 쪽에만 뒷부분이 더 있음, 12곡이 아직 다름.
**음표가 전부 맞는 곡: 291 / 303 (96%).**

> `.R36` / `.G36` / `.G18`(Recomposer의 다른 형식)은 샘플 파일이 없어서 한 번도
> 확인하지 못했다. 이 문서의 내용은 `.RCP`에만 해당한다.

## 1. 곡 머리

| 오프셋 | 크기 | 내용 | |
|---|---|---|---|
| `0x000` | 32 | `"RCM-PC98V2.0(C)COME ON MUSIC"` | ✅ |
| `0x020` | 64 | 곡 제목 (**Shift-JIS**) | ✅ |
| `0x1C0` | 1 | 해상도 (4분음표당 틱, 보통 48) | ✅ |
| `0x1C1` | 1 | 기본 템포 (BPM) | ✅ |
| `0x1C2` | 1 | 박자 분자 | ✅ |
| `0x1C3` | 1 | 박자 분모 | ✅ |
| `0x1C5` | 1 | **곡 전체 조옮김, 부호 있음** (`0xF4` = −12) | ✅ |
| `0x1C6` | 16 | CM-64/MT-32 셋업 파일 이름 (`.CM6`) — `.CM6` 내용은 아직 읽지 않음 | ❓ |
| `0x1D6` | 16 | **SC-55 셋업 파일 이름 (`.GSD`)** | ✅ |
| `0x406` | 8 × 48 | 사용자 SysEx 8개 (`F0`로 시작, `F7`로 끝남) | ✅ |
| `0x586` | … | 트랙 데이터 시작 | ✅ |

✅ **제목은 Shift-JIS로만 읽는다.** 한국어 우선 디코더에 넣으면 전각 로마자
(`Ｂａｍ`)가 우연히 올바른 완성형 한글이 되어 엉뚱한 한글로 나온다.

✅ `0x1C5` 곡 조옮김: 303곡 중 **일치하던 200곡은 모두 0**이었다. `CROSS_4`는 −12,
`LOVE`는 +2를 갖고 있었고, 이것을 무시하면 모든 멜로디 채널이 그만큼 어긋난다.

## 2. 트랙 머리 — 44바이트 (48이 아님)

| 오프셋 | 크기 | 내용 | |
|---|---|---|---|
| `+0` | 2 | 트랙 크기 (머리 포함) | ✅ |
| `+2` | 1 | 트랙 번호 | ✅ |
| `+3` | 1 | 리듬 플래그 | ✅ |
| `+4` | 1 | MIDI 채널 (0~15) | ✅ |
| `+5` | 1 | **트랙 조옮김** (아래) | ✅ |
| `+6` | 1 | **트랙 시작을 몇 틱 늦춤** (부호 있음) | ✅ |
| `+7` | 1 | 모드. **비트 0 = 뮤트** | ✅ |
| `+8` | 36 | 트랙 이름 | ✅ |

✅ **머리는 44바이트다.** 48로 읽으면 모든 트랙의 첫 이벤트가 사라진다. 첫
이벤트가 무엇이냐에 따라 증상이 달라서 원인을 찾기 어려웠다. `BAMBOO.RCP`의
한 트랙은 192틱 쉼표, 에코 트랙은 200틱 쉼표를 잃었다.

✅ **트랙 조옮김 `+5`**: **비트 7이 켜져 있으면 "조옮김 없음"**이다(`0x80`만이
아니라 비트 7 전체). 64~127은 −64~−1이다(116 = −12). `>= 64 ? −128`로 계산하면
`0x80`은 우연히 맞지만 140(`0x8C`)은 12반음, 129는 1반음 높게 나온다.

✅ **트랙 지연 `+6`**: 드럼 트랙에 3, 다른 네 트랙에 1~2가 들어 있던 곡에서, 채널별로
어긋난 틱 수가 이 값과 13채널 모두 정확히 일치했다.

✅ **뮤트 `+7` 비트 0**: 시퀀서에서 뮤트한 트랙도 음표가 파일에 그대로 남아 있다.
참조 MIDI에는 그 음표가 **하나도 없다.** 다른 비트(2, 4, 32, 56)는 뮤트가 아니다 —
그런 트랙은 모두 참조에 있다.

## 3. 이벤트 — 4바이트

```
[명령, step, gate, velocity]
```

`step`은 다음 이벤트까지의 틱 수(시간이 흐르는 양), `gate`는 음 길이다.

### 음표 (`0x00`~`0x7F`)

명령이 음 번호다. 조옮김 = 트랙 `+5` + 곡 `0x1C5`. **MIDI 채널 10과 이름에
DRUM/PERC가 들어간 트랙은 조옮김하지 않는다.**

✅ **gate가 step보다 길면 붙임줄(tie)이다.** 같은 음높이의 다음 음표로 이어지고,
다시 치지 않는다. 사슬의 마지막 음표가 끝나는 시점을 정한다. `3DAYS.RCP`는
step 192에 gate 193처럼 딱 1틱 넘기는 방식으로 붙임줄을 쓴다.

### 명령

| 명령 | 뜻 | 시간 흐름 | |
|---|---|---|---|
| `0x80`~`0x87` | 사용자 SysEx 0~7번 그대로 보냄 | step | ✅ |
| `0x90`~`0x97` | 사용자 SysEx 0~7번. 그 안의 `0x80`은 gate, `0x81`은 velocity로 바꿔 넣음 | step | ✅ |
| `0x98` | ❓ **정체 불명.** 예전엔 `0xFC`와 같게 처리했으나 틀림 (아래) | step | ❓ |
| `0xDD` | Roland 주소 상위 2바이트 = gate, velocity | step | ✅ |
| `0xDE` | Roland 주소 마지막 바이트 = gate, 값 = velocity → **GS 파라미터 쓰기 1개** 전송 | step | ✅ |
| `0xDF` | Roland 장치 번호 = gate, 모델 번호 = velocity | step | ✅ |
| `0xE1` | 뱅크 선택 (CC0 = velocity) | step | ✅ |
| `0xE2` | **뱅크 + 프로그램**: CC0 = velocity, CC32 = 0, 프로그램 = gate. **템포가 아님** | step | ✅ |
| `0xE6` | **채널 변경. 값은 gate, 1부터 셈** (1~16) | step | ✅ |
| `0xE7` | **템포 = 곡 기본 템포 × gate / 64.** BPM 값이 아니라 비율 (64 = 1배) | step | ✅ |
| `0xEA` `0xEB` `0xD2` | 컨트롤 체인지 (번호 = gate, 값 = velocity) | step | ✅ |
| `0xEC` `0xD3` | 프로그램 체인지 (프로그램 = gate, 뱅크 = velocity) | step | ✅ |
| `0xEE` `0xD0` | 피치 벤드 (LSB = gate, MSB = velocity) | step | ✅ |
| `0xF5` | 조표. **시간 안 흐름** | 없음 | ✅ |
| `0xF6` `0xF7` | 주석 문자열. **세 바이트 모두 글자, 시간 안 흐름** | 없음 | ✅ |
| `0xF8` | 반복 끝. step = **전체 반복 횟수** (시간 아님) | 없음 | ✅ |
| `0xF9` | 반복 시작 (시간 아님) | 없음 | ✅ |
| `0xFC` | **같은 마디 반복** (4절) | 마디만큼 | ✅ |
| `0xFD` | 마디 끝. **step은 시간이 아님** | 없음 | ✅ |
| `0xFE` | 트랙 끝 | — | ✅ |

"시간이 안 흐르는" 명령들은 모두 한때 step을 더해서 문제가 났다.
`0xFD`는 마디마다 1틱씩 밀렸고(`BAMBOO`에서 966번), `0xF5`는 3틱씩 쌓였고,
주석 하나의 첫 글자가 `0x0C`였던 탓에 드럼 트랙 전체가 12틱 늦었다.

`0xDF`/`0xDD`/`0xDE` 세 개가 모여 `F0 41 <장치> <모델> 12 <주소3> <값> <체크섬> F7`
한 개가 된다. 이것을 빠뜨리면 `BAMBOO`의 SysEx 211개 중 156개가 사라진다.

## 4. `0xFC` 같은 마디 반복 — 가장 까다로운 명령

✅ `step`은 마디 번호처럼 보이지만 **따라가는 것은 뒤의 두 바이트**다.
`gate | (velocity << 8)` = **트랙 시작(44바이트 머리 포함)에서 센 바이트 위치.**
마디 번호로 찾으면 드럼 트랙 130개 중 81개에서 번호가 가리키는 마디와 위치가
가리키는 곳이 달랐다(14/81만 일치).

✅ **반복 안에서 만난 반복은 꼬리 호출(tail call)이다.** 돌아올 곳을 하나 더 쌓지
않고 점프만 한다. 그래서 `0xFC` 하나는 사슬이 아무리 길어도 **정확히 한 마디**를
연주한다. 마디 끝을 "다음 `0xFD`"로 정하면 안 된다. `6PONGI4`의 한 채널에는
`0xFD` 없이 `0xFC`가 50개 이어진 곳이 있다(한 마디에 하나씩, 각각 앞의 다른 마디를
가리킴).

✅ **반복을 끝내는 기준은 "위치"다.** 반복으로 점프해 간 **바로 그 바이트**에 있는
`0xFC`는 "이 마디도 복사본"이므로 따라간다. 그보다 **뒤에서** 만난 `0xFC`는 다음
마디가 시작된 것이므로 반복을 끝낸다. 이 규칙으로 303곡 중 일치가 219 → 225곡이
됐고, 깨진 곡은 없었다. 더 단순한 규칙 두 개(아무 `0xFC`에서나 끝내기, 박자로 한
마디 길이 재기)는 둘 다 곡을 잃었다.

✅ **같은 `0xFC`를 한 사슬 안에서 두 번 타지 않는다.** 사슬이 자기 자신으로 닫히는
파일이 있다(`IKDT2_20`). 이 보호 없이 따라가면 15 KB 파일이 음표 574,168개가 된다
(참조는 3,989개). 깊이 제한을 두면 제한에서 같은 오류가 다시 생기므로 쓰지 않는다.

### `0x98`은 `0xFC`가 아니다

한때 `0x98`을 `0xFC`와 같게 처리했는데, 근거가 없었다. 라이브러리 213곡 중 169곡에
`0x98`이 있고, `YUNO2488.RCP`에서는 그 "위치" 값이 대부분 머리 안쪽이거나 4바이트
정렬이 아니었다(진짜 `0xFC` 위치는 모두 정렬됨). 우연히 통과한 두 개가 순환을 만들어
**음표 0개, 트랙마다 CC 3만~6만 개**가 나왔다. 지금은 step만큼 시간을 보내고 넘어간다.
❓ `0x98`을 쓰면서 참조 `.MID`가 있는 파일이 나오면 정체를 알 수 있다.

## 5. `.GSD` — SC-55 셋업 파일 (소리의 절반)

곡 머리 `0x1D6`에 적힌 이름의 파일이 곡 옆에 있다. 이것 없이 재생하면 파트 음색,
볼륨, 팬이 기본값이 되고, 어느 채널이 리듬인지도 모른다.

✅ 참조 MIDI는 이 파일을 **두 가지로** 보낸다. SC-55만 알아듣는 벌크 덤프와,
같은 설정을 일반 채널 메시지로 한 번 더. 다른 음원도 설정을 받게 하기 위해서다.

### 5-1. 파트 블록 (16개, 기준 `0x0035`, 간격 `0x7A`)

| 파일 오프셋 | 내용 | 보내는 방법 |
|---|---|---|
| `+0x00` | 보이스 리저브 | `40 01 10` (아래 5-4) |
| `+0x01` | **톤 뱅크** | CC0 (CC32는 항상 0) |
| `+0x02` | 톤 번호 | 프로그램 체인지 |
| `+0x03` | **수신 채널** — 이 블록이 어느 채널을 설정하는지 | |
| `+0x16` | 리듬 파트 여부 | `40 1n 15 vv` |
| `+0x1A` | 레벨 | CC7 |
| `+0x1D` | 팬 | CC10 |
| `+0x22` | 코러스 양 | CC93 |
| `+0x23` | 리버브 양 | CC91 |
| `+0x43` | 피치 벤드 범위 (+64 치우침) | RPN 0,0 |

✅ **블록 순서가 곧 MIDI 채널이 아니다.** `+0x03`이 채널을 정한다. `3DAYS.GSD`는
블록 1과 9가 서로의 채널을 맡는다. 순서대로 쓰면 16개 중 14개는 맞아 보이고 두 개만
몰래 바뀐다.

✅ 톤 뱅크는 `+0x01`이다. `+0x00`(보이스 리저브)은 대부분 0이라 틀린 위치를 읽어도
맞아 보였다. 122개 오프셋을 전부 대조해서 딱 하나로 좁혔다.

### 5-2. 파일의 파트 블록 → SC-55 파트 블록

파일 블록은 122바이트, SC-55의 파트 영역은 **112바이트**다. 값은 같아도 **자리가
다르다.** 그대로 복사하면 128바이트 중 66~71바이트가 엉뚱한 파라미터에 들어가
SC-55가 오류를 띄우고 소리가 안 난다. 대부분은 고정값(0x40, 0x00)이고, 파일에서
가져오는 자리는 다음과 같다.

| SC-55 | 파일 | 내용 |
|---|---|---|
| `00`~`01` | `01`~`02` | 톤 뱅크, 톤 번호 |
| `02`~`03` | 고정 `FF FF` | |
| `04` | `03` | 수신 채널 |
| `05` | 파일 `16`이면 `B0`, 아니면 `81` | 리듬 파트 여부 |
| `06` | `17` | 키 시프트 |
| `07` | 고정 `80` | |
| `08` | `1A` | 레벨 |
| `09` | `1D` | 팬 |
| `0A`~`0B` | `1B`~`1C` | |
| `0C` | `19` | |
| `0D` | `1F` | |
| `0E`~`17` | `22`~`2B` | 코러스, 리버브, **톤 모디파이** |
| `26`~`27` | `20`~`21` | |
| `2D`~`36` | `3C`~`45` | 스케일 튜닝 |

✅ 이 표로 참조가 있는 두 곡의 파트 블록 **32개를 `.GSD`만으로 다시 만들면
32개 모두 바이트까지 같다.**

벌크 덤프 주소 간격은 `0x90 + 0xE0 × 슬롯`이다. `0xE0`은 니블 224개 = 112바이트다.
참조의 메시지 크기(137, 105바이트)도 이것과 맞는다.

### 5-3. 드럼 맵

✅ 한 맵은 **음 27부터 83개 음**, 음마다 4바이트다. 맵 1은 `0x07D6`, 맵 2는
`0x0922`에서 시작한다. 네 열이 각각 **두 개의 메시지**(음 0~63, 음 64~127)로 나가고,
블록 번호는 `02/03`, `06/07`, `08/09`, `0A/0B`, 두 번째 맵은 여기에 `0x10`을 더한다.
쌍의 두 번째 메시지 첫 값은 음 0이 아니라 **음 64**다(`0x086A` = `0x07D6 + 37 × 4`).
이것을 놓치면 "한 곳에서 값 하나가 어긋난다"처럼 보인다. 16개 블록을 다시 만들면
32/32 일치한다.

드럼 맵을 빠뜨리면 드럼의 음별 레벨(79~127)이 모두 기본값이 되어 **드럼이
통째로 크게** 들린다.

### 5-4. 보이스 리저브

✅ `40 01 10`은 24개 보이스를 파트에 나눠 주는 메시지다. 각 파트 블록의 `+0x00`을
**파일 순서대로 놓되 0번과 10번을 맞바꾼다.** 122개 오프셋 × 순서 3가지를 두 곡에
대입해 보면 답이 이것 하나만 남는다. 맞바꾸지 않으면 `3DAYS`의 드럼 파트가 보이스를
**하나도** 못 받는다.

## 6. JMPlayer 변환기의 약속 (포맷이 아니라 우리 선택)

- 셋업을 보낼 **도입부 576틱을 120 BPM으로** 두고, 음악이 시작되는 틱에서 곡 템포로
  바꾼다. 참조 MIDI가 이렇게 한다. `.GSD`가 없는 곡은 도입부를 생략한다.
- 참조 MIDI에 없는 **GS 리셋을 맨 앞에 보낸다.** 참조는 이미 리셋된 모듈에서
  녹음됐지만, 실제로는 앞 곡이 남긴 설정이 남아 있을 수 있다.
- 셋업 메시지 간격은 **MIDI 전송 시간**(`1 + 크기/32` 틱)으로 벌린다. 한꺼번에 보내면
  실제 SC-55가 따라오지 못한다.
- **같은 틱의 이벤트는 파일에 적힌 순서를 지킨다(안정 정렬).** `3DAYS`는 한 틱에
  "음 켜기 → 프로그램 체인지 → 음 켜기" 순서로 두 음색을 겹친다. 음 끄기만 앞으로
  당긴다.

## 7. 아직 모르는 것

- ❓ `0x98` 명령.
- ❓ 트랙 머리 `+7`의 비트 0 외 비트(2, 4, 32, 56).
- ❓ 반복 끝 `0xF8`의 step = 0 (반복 횟수 없음). 참조 변환기는 이때 곡 끝에
  반복 구간을 **네 마디** 더 붙인다(AK68GS 계열에서 측정, 앞에서 말한 "뒷부분만
  더 있는" 66곡이 대부분 이 경우). 파일의 정보가 아니라 그 변환기의 관례로 보고
  따라 하지 않았다.
- ❓ 남은 12곡의 불일치 (`GOKU2` +5,403음, `BARE1_1` +2,697음, `FZ_PORTX` −893음 등).
- ⚠️ 참조 `.MID`도 틀릴 수 있다. `EM_OP`의 드럼 트랙은 틱 13,636 뒤에 파일에 분명히
  있는 음표 400개를 참조가 빠뜨렸다. 불일치를 우리 탓으로 단정하기 전에 파일에
  실제로 무엇이 있는지 먼저 볼 것.
