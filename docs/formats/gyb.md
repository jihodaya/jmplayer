# `.GYB` — 가요방 노래방 (GAYOBANG)

> **작성**: JJOME (GitHub [jihodaya](https://github.com/jihodaya)) — [JMPlayer](https://github.com/jihodaya/jmplayer) 포맷 분석 기록

> **근거**: GAYOBANG.EXE 디컴파일, DOSBox에서 원본으로 녹음한 소리와의 비교, 라이브러리 334곡 실측.
> 표시: ✅ 확인됨 · 📏 실측으로 맞춤 · ❓ 미확인 ([README](README.md) 참고)

1990년대 국산 DOS 노래방 프로그램 **가요방**(GAYOBANG.EXE)의 곡 파일이다.
애드립(OPL2/OPL3) FM 음원으로 연주하고, 파일 안에 **악기 데이터와 가사**를 함께
담고 있다. 옥소리 노래방(NORE45)과 **같은 OPL 드라이버**를 쓰기 때문에 여기서
밝힌 재생 규칙 대부분은 `.OKA`에도 그대로 적용된다([oka-okm-okw.md](oka-okm-okw.md)).

---

## 1. 전체 구조

```
0x00            헤더 (64바이트)
0x40            (매직 0x04만) 보조 헤더 15바이트
0x40 또는 0x4F  전역 이벤트 (템포)
                채널 블록 × 11 (채널 0~10)
                악기 레코드 × N (각 38바이트)
                가사 (파일 끝까지)
```

✅ 매직이 `0x04`인 파일은 64바이트 헤더 뒤에 15바이트 보조 헤더가 더 있어서
본문이 `0x4F`에서 시작하고, `0x03`인 파일은 `0x40`에서 바로 시작한다
(GAYOBANG.EXE `FUN_28a1_113b`, `DAT_445a_8d6a = 0x0F`).

## 2. 헤더

| 오프셋 | 크기 | 내용 | |
|---|---|---|---|
| `0x00` | 1 | 매직: `0x03` 또는 `0x04` | ✅ |
| `0x01` | 25 | 곡 제목, **조합형 한글**, NUL로 끝남 | ✅ |
| `0x28` | 1 | tickBeat 제수 (보통 4). 재생 속도에 들어감 (아래 4절) | ✅ |
| `0x2A` | 1 | 박자 분자. **가사 한 줄의 박 수**로도 쓰임 (7절) | ✅ |
| `0x2B` | 1 | 박자 분모 (4) | ✅ |
| `0x2D` | 1 | **리듬 모드 플래그**. 0이 아니면 OPL 리듬 모드(채널 11개), 0이면 멜로디 9채널 | ✅ |
| `0x2E` | 1 | **조 기준음** (보통 60). 실제 음 = 명령값 − `[0x2E]` + 60 | ✅ |
| `0x32` | 2 | 이름이 "템포"처럼 보이지만 **템포가 아님**. 60 BPM 곡에서도 200 BPM 곡에서도 100이 들어 있음 | ❓ |
| `0x34` | 4 | **기본 템포 × 100** (예: 14000 = 140 BPM) | ✅ |
| `0x3C` | 2 | 악기 레코드 개수 | ✅ |

`0x2D`/`0x2E`/`0x32`의 위치는 GAYOBANG이 곡 헤더를 메모리 `0x8d2c`에 두고
`0x8d59`(= 파일 `0x2D`)를 리듬 설정 함수 `FUN_255a_1222`에 넘기는 것에서
확인했다. 이웃한 `0x8d5a`에 60, `0x8d5e`에 100이 있어 기준 주소가 맞다는 것을
뒷받침한다. ✅

## 3. 본문

### 3-1. 전역 이벤트 (템포)

```
u16  개수
[ u16 틱, u16 값 ] × 개수
```

✅ 값은 **기본 템포에 대한 백분율**이다. 100이면 헤더 템포 그대로,
50이면 절반 속도다.

✅ **값 1000은 템포다.** 라이브러리 27곡 중 8곡이 틱 0에 1000을 둔다.
GAYOBANG은 악보에 "♩=1400"(140 BPM 곡일 때)으로 표시하고 실제로 그 속도로 빨리
지나간다. 소리가 안 들리는 이유는 템포가 아니라, 그 구간 동안 모든 채널의 볼륨이
0이기 때문이다(틱 0에 볼륨 0, 틱 32에 실제 볼륨). 이 구간을 건너뛰거나 따로
처리하면 곡 시작이 약 1.5초 틀어진다.

### 3-2. 채널 블록 (채널 0~10 순서대로)

```
u8   채널 번호 (반드시 0, 1, 2 ... 순서)
u16  이 채널의 끝 틱
[ u8 명령, u8 길이 ] ...   길이 합이 끝 틱에 닿을 때까지
u16  악기 변경 개수    [ u16 틱, u8 슬롯, u8 0 ] × 개수
u16  볼륨 개수         [ u16 틱, u8 볼륨, u8 0 ] × 개수
u16  피치 개수         [ u16 틱, u8 피치, u8 0 ] × 개수
```

✅ 위 구조는 GAYOBANG `FUN_28a1_18f0`의 읽기 순서와 같다.

**음표 명령 (명령, 길이)**

| 명령 값 | 뜻 | |
|---|---|---|
| `0x00` | 쉼표. 울리던 음을 끈다 | ✅ |
| `0x01`~`0x78` | 음 켜기. 실제 음 = 명령 − `[0x2E]` + 60 | ✅ |
| `0x79` 이상 | 아래 참고 | ❓ |

❓ **`0x79` 이상은 해석이 둘로 갈린다.** JMPlayer 재생 엔진은 "지금 음을 계속
유지(아무것도 안 함)"로 읽고, 변환기 jmpconv는 "(값 − 0x79) 음을 끄기"로 읽는다.
jmpconv 쪽은 원본이 만든 변환 결과와 음표 74,566개가 모두 일치했지만, 두 해석이
실제 소리에서 차이가 나는 곡은 아직 찾지 못했다. 둘 다 "한 채널에 한 음"이라는
전제는 같아서 대부분의 곡에서 결과가 같다.

길이 단위는 틱이고, 한 명령이 255틱보다 길면 같은 명령을 이어서 쓴다.

**볼륨**: 파일 값 0~100. GAYOBANG은 `채널볼륨 = 마스터 × 값 / 100` (127에서 자름)
으로 계산해서 오퍼레이터 TL에 **선형으로** 적용한다 (`FUN_255a_0245`, `FUN_255a_082e`):

```
TL' = 63 − ((볼륨 × (63 − TL) + 64) >> 7)
```

✅ dB 표를 쓰는 로그 곡선이 아니다. 어떤 오퍼레이터에 적용하는지는 3-3 참고.

**피치 벤드**: 파일 값 0~20, **10이 중앙**. GAYOBANG은 `값 × 0x333`(한 칸에 819)
을 AdLib 라이브러리의 14비트 벤드(중앙 `0x2000`)로 넘긴다 (GAYOBANG.c:30115). ✅

### 3-3. 채널 배치와 리듬 모드

리듬 모드(`[0x2D] ≠ 0`)일 때:

| 채널 | 0~5 | 6 | 7 | 8 | 9 | 10 |
|---|---|---|---|---|---|---|
| 역할 | 멜로디 | 베이스 드럼 | 스네어 | 탐탐 | 심벌 | 하이햇 |

✅ `[0x2D] = 0`이면 리듬 모드 없이 멜로디 9채널이다. 라이브러리에서
`WITHLOVE.GYB` 한 곡이 여기에 해당한다.

## 4. 재생 속도

✅ 틱이 도는 속도:

```
BPM   = ([0x34] / 100) × (전역이벤트값 / 100)
틱/초 = BPM × [0x28] / 60
```

AdPlug가 IMS에 쓰는 공식(`basicTempo × tickBeat / 60`)과 같은 모양이다.
`[0x28]`을 놓치기 쉽다. 샘플 곡이 모두 4였기 때문에 한동안 상수로 착각했다.

## 5. 원본 드라이버의 동작 — 재현할 때 지켜야 할 것

GAYOBANG의 OPL 드라이버를 디컴파일해서 확인한 동작이다. 일반적인 AdLib
재생기(AdPlug의 composer 등)와 **다른 점**만 적었다.

1. ✅ **곡에 들어 있는 악기를 쓴다.** 슬롯 이름으로 뱅크를 찾아 덮어쓰면 안 된다.
   DOS GAYOBANG에서 뱅크 파일을 지워도 라이브러리 전체가 정상 재생된다.
   이름으로 뱅크를 찾게 했더니 **88%의 곡에서 악기가 바뀌었다.** 뱅크를 보는
   경우는 레코드가 비어 있을 때뿐이다([opl-instrument.md](opl-instrument.md)).
2. ✅ **악기 변경이 울리던 음을 다시 치지 않는다.** 악기 레지스터만 바꾸고
   엔벨로프는 그대로 이어진다. 다시 치면 음마다 타격음이 한 번 더 난다
   (`FUN_255a_06ad` / `_07df`는 key off/on으로 감싸지 않음).
3. ✅ **리듬 채널 두 개의 주파수는 곡 시작 때 한 번 정한다.** 채널 7(스네어+하이햇)은
   음 31, 채널 8(탐탐+심벌)은 음 24를 GAYOBANG 자신의 음 표로 변환한다.
   결과는 **fnum 517 / block 2 = 98.0 Hz**, **fnum 690 / block 1 = 65.4 Hz**다.
   AdPlug는 이 두 채널을 정확히 **한 옥타브 높게**(195.3 Hz / 130.1 Hz) 잡는다.
   드럼 음을 칠 때도 GAYOBANG은 `0xBD` 레지스터의 키 비트만 건드리고 주파수는
   다시 쓰지 않는다.

   > 음 표 읽는 법: `0x445a:0x143a`에 반음당 워드 하나, `0x15ba`에 음별 블록,
   > `0x161a`에 행 인덱스. **최상위 비트가 켜진 워드는 "한 블록 위의 F-number"라는
   > 뜻**이다. 이 부분을 잘못 읽기 쉽다.
4. ✅ **덧셈 합성(additive) 악기는 모듈레이터 볼륨도 같이 줄인다.** GAYOBANG은
   오퍼레이터가 캐리어이거나, 그 오퍼레이터의 연결 비트가 0(덧셈)이거나, 리듬
   드럼 오퍼레이터이면 채널 볼륨을 적용한다. AdPlug는 캐리어만 줄인다.
   라이브러리 악기 403개 중 133개(33%)가 덧셈 합성이다.
5. ✅ **피드백/연결 레지스터(`0xC0`)는 모듈레이터 값에서 쓴다.** `FUN_255a_097c`는
   "캐리어인가" 배열(`DAT_445a_1363`)이 0인 오퍼레이터에만 `0xC0`을 쓴다.
   캐리어 쪽 피드백 칸은 쓰레기 값이다(뱅크 6,009개 중 5,268개가 0~7 범위 밖).
6. ✅ **곡 시작 때 레지스터 `0x08`에 `0x40`(NOTE-SEL)을 쓴다.** 엔벨로프 속도의
   키 스케일링이 달라진다. AdPlug의 초기화는 이 비트를 끈 채로 둔다.
7. ✅ **파형은 2비트만 쓴다.** 악기 로더가 `record[13] = waveform & 3`로 자른다.
   OPL3 모드를 켠 에뮬레이터에 3비트를 그대로 넘기면 원본이 낼 수 없는 파형이 나온다.
8. ✅ **채널 초기 악기**: 곡을 시작하기 전에 멜로디 채널(0~5)에는 내장 악기 0번,
   드럼 채널(6~10)에는 내장 악기 1~5번을 넣는다 (`FUN_255a_101b`).
9. ✅ **OPL3 모드 이중 발음**: OPL3에서는 두 번째 포트(`0x38a`)에 같은 음을 벤드를
   `0x600`(+18.75센트) 올려 한 번 더 내고, 모드 3 이상에서는 9/10 세기로 낸다.
   실제로 있는 동작이지만 대역 균형에 미치는 영향이 0.08 dB여서 JMPlayer는
   구현하지 않았다.

## 6. 악기

헤더 `0x3C`의 개수만큼 38바이트 레코드가 채널 블록 바로 뒤에 온다. 구조와 빈
레코드 처리는 [opl-instrument.md](opl-instrument.md)에 따로 정리했다.
슬롯 0은 보통 비어 있고, 악기 변경 명령의 값이 이 슬롯 번호다.

## 7. 가사

✅ 악기 레코드 바로 뒤부터 파일 끝까지가 가사다.

- **국내판**: 조합형 한글, **한 줄 = 고정 75바이트**. 한 글자는 2바이트(두 칸).
- **수출판(영어)**: 평문 ASCII, 한 칸에 1바이트. **NUL 5개 이상이 줄 바꿈**이다.

✅ **가사 하이라이트 속도** — 원본은 한 줄씩 보여 주고, 한 줄이 일정한 틱 동안
머문다.

```
한 줄의 틱  = [0x28] × [0x2A] × 4      (FUN_28a1_0436, FUN_2dcf_2fe8)
글자 위치의 틱 = 바이트 위치 × [0x28] × [0x2A] × 4 / 75
```

즉 하이라이트는 한 줄 75칸을 일정한 속도로 왼쪽에서 오른쪽으로 쓸고 지나간다.
템포와 상관없이 **박 단위**로 움직인다. `[0x2A]`를 4로 고정하면 3/4박자
(영어판 `P_G_005`~`010`)나 2/4박자(`P_G_004`) 곡에서 가사가 점점 늦어진다.

📏 JMPlayer는 여기에 영어판 1.75박, 줄 첫 글자 1박의 앞당김을 더한다. 귀로 맞춘
값이다.

## 8. `GYB.LST` — 곡 목록 파일

곡 폴더에 함께 있는 목록 파일. 곡 파일 안에 제목이 없을 때 여기서 찾는다.

```
0x00  8바이트 머리
0x08  레코드 × N, 40바이트 간격
        +0   24  제목 (조합형)
        +24  12  파일 이름 (8.3 형식, ASCII)
        +36   4  ❓
```

## 9. `.OKA`와 같은 곡이 다르게 들리는 이유

같은 곡이 `.GYB`와 `.OKA` 두 가지로 있는 경우가 많다(한쪽을 다른 쪽으로 변환한
것). 소리가 다르면 재생기가 아니라 **파일이 다른 것**이다. `BACKPUSA`로 실측:

- 음 켜기 개수(3,577)와 악기 17개는 **바이트까지 같다.**
- `.GYB`에는 **쉼표가 1,994개** 있고 `.OKA`에는 음 끄기가 **0개**다. 변환하면서
  쉼표가 전부 사라져서, 원래 조용해야 할 곳에서 음이 계속 울린다.
- 그 결과 `.OKA`는 40~160 Hz가 1.8~2.5 dB 크게 나온다.

파일에서 정보가 사라진 것이라 재생기로는 되돌릴 수 없다. 두 파일이 다 있으면
`.GYB` 쪽을 재생하는 것이 맞다.

피치 벤드 폭도 두 프로그램이 원래 다르다. GYB는 한 칸 819(`× 0x333`), OKA는
NORE45가 2.5배로 넓힌 뒤 750이다. 두 값 모두 원본 코드에서 나온 것이라
**원래 그렇게 다른 것**이 맞다.

## 10. 아직 모르는 것

- ❓ 헤더 `0x32`의 정체 (항상 100 근처).
- ❓ 음표 명령 `0x79` 이상의 정확한 의미 (3-2절).
- 📏 **드럼 −4.5 dB**: 리듬 오퍼레이터 다섯 개를 4.5 dB 줄이면 실기 녹음과
  80 Hz~12 kHz 전 대역이 0.6 dB 안으로 맞는다. 하지만 **녹음 한 곡에 맞춘 값**이고,
  원본 코드에서 나온 값이 아니다. 두 번째 곡의 실기 녹음이 있어야 확정할 수 있다.
- ❓ 곡 끝부분이 DOS보다 약 5 dB 작고 1.5초 짧게 끝나는 원인.
